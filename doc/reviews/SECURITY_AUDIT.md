## 二、构建安全

### 2.1 编译器加固

当前 MSVC 构建需确认以下选项：

| 选项 | 状态 | 说明 |
|------|------|------|
| `/GS` | 默认开启 | 缓冲区安全检查 |
| `/guard:cf` | **未启用** | 控制流保护（CFG） |
| `/DYNAMICBASE` | 默认开启 | ASLR |
| `/NXCOMPAT` | 默认开启 | DEP |
| `/HIGHENTROPYVA` | 默认开启（x64） | 高熵 ASLR |

**建议**：在 `CMakeLists.txt` 中为 MSVC 添加 `/guard:cf` 与 `/sdl`。

### 2.2 依赖来源

- 依赖统一通过 **vcpkg** 获取，版本由 vcpkg 基线锁定
- 未使用 `vcpkg.json` 清单模式，版本随基线变动

**建议**：添加 `vcpkg.json` 锁定关键依赖版本。

## 三、代码安全

### 3.1 静态分析

- **CodeQL**：已在 GitHub Actions 中配置（C/C++ 分析），每次推送与每周定时运行
- **Dependabot**：已配置，每周检查 GitHub Actions 依赖更新

### 3.2 已知风险点

| 风险 | 位置 | 说明 | 缓解 |
|------|------|------|------|
| 硬编码绝对路径 | `vncviewer.cxx:598`、`winvnc.cxx:258` | `C:\temp` 日志回退 | 低风险，建议统一日志目录 |
| 命令注入 | `UpdateCheckerUnix.cxx` | 通过 `system()` 执行 curl | 已对参数做单引号转义，风险可控 |
| 临时文件 | `UpdateCheckerWin32.cxx` | 更新脚本写入 `%TEMP%` | 建议校验下载包签名 |

### 3.3 自更新安全

当前自更新流程：
1. 通过 HTTPS 请求 GitHub API（证书校验由 WinHTTP 默认执行）
2. 下载安装包到 `%TEMP%`
3. 执行静默安装

**风险**：
- **未校验安装包签名**：若 GitHub 账号或网络被攻破，可分发恶意安装包
- **未校验哈希**：无法检测下载损坏或篡改

**建议（P0）**：
1. 发布时对安装包做 **Authenticode 签名**
2. 客户端下载后校验签名与哈希
3. 在 Release 元数据中提供 SHA-256

## 四、发布流程

### 4.1 自动化

- 推送 `v*` 标签自动构建 Windows x64 安装包
- 自动创建 GitHub Release

### 4.2 完整性

- **未签名**：安装包无数字签名，Windows 会显示"未知发布者"
- **无 SBOM**：未生成软件物料清单

**建议**：
1. 申请代码签名证书（EV 或 OV）
2. 生成 SBOM（CycloneDX 格式）
3. 发布 Note 中附 SHA-256 校验值

## 五、审计结论

### 总体评价

TuPigVNC v0.0.1 作为品牌化首个版本，基础安全配置到位（Secret Scanning、CodeQL、分支保护），但**自更新的完整性与发布签名**是当前最大缺口。

### 优先处理项

| 优先级 | 事项 | 影响 |
|--------|------|------|
| P0 | 安装包数字签名 + 客户端校验 | 防止供应链攻击 |
| P0 | 自更新 SHA-256 校验 | 防止下载篡改 |
| P1 | 启用 `/guard:cf` 编译加固 | 提升抗漏洞利用能力 |
| P1 | 添加 `vcpkg.json` 锁定依赖 | 构建可复现 |
| P2 | 生成 SBOM | 供应链透明度 |
| P2 | 配置必需状态检查 | 防止未通过 CI 的代码合入 |

### 后续行动

1. 短期（1 周）：完成 P0 项，补齐自更新的完整性校验
2. 中期（1 月）：P1 项，完善构建与依赖管理
3. 长期：P2 项，建立完整的供应链安全体系
